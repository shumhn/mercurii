# Mercury agents: devnet build plan

Mercury has one user-facing Finance Agent with invoice review, payroll checks, payment drafts, and an optional x402 purchase tool. The x402 tool uses a separate, tightly funded signing boundary.

## 1. Finance Assistant (human-facing)

The agent answers questions from private company state and prepares work for the authenticated user. It resolves the wallet's active grant before each private tool call. The model chooses among role-filtered tools; Mercury code validates every call, executes it, and returns a narrow result. A revoked grant or parent grant stops the next tool call.

Current tools: last private treasury snapshot; selected payment request status; payroll run status and roster readiness; invoice extraction against a registered vendor; an unsigned payment draft for the user-selected payee and exact amount; and optional x402 offer inspection followed by a Founder-assigned API purchase. The agent must inspect the live price before its purchase tool is allowed. Each tool enforces the caller's role and scope. A wallet signs a one-use, five-minute challenge before each run. The caller supplies their own TEE access token. The endpoint requires `MERCURY_ENABLE_FINANCE_ASSISTANT=1`.

Next actions, in order:

1. Add invoice document intake, review evidence, and a persistent case state from draft through settlement. The current invoice tool accepts text and reuses the existing duplicate/changed-terms journal. Keep any future document encrypted outside chain state.
2. Explain failed payroll items beyond the current request-state and readiness summaries. The agent must never choose a salary, approve its own request, or release payroll.
3. Extend the encrypted 24-hour conversation session with richer sourced answers from scoped tool results. The current session remembers only recent verified answers and the selected payment/payroll reference; it never reuses a payment amount or approval. Do not put the entire company journal into model context.

The model chooses a tool, but Mercury code constructs factual answers from the permitted private read. A model-only answer is not presented as a company fact. Mercury code and the onchain program decide grant validity, recipient, limits, payment ID, signing requirements, and settlement. `Send this` prepares a transaction; it is not a signature.

## 2. Tool Spender (background worker)

This is a separate signing boundary for purchases made to finish an assigned task, such as an approved paid API. Founder funds a small isolated balance and can revoke it. Each purchase needs an asset/network check, a per-purchase cap, a period cap, an approved service and recipient, expiry, a task reference, and a final receipt. The worker never has the company treasury key.

Mercury has an x402 V2 `exact` devnet client adapter, unit tests, a full SDK handshake against a local mock merchant, and a real paid devnet proof: the isolated signer bought PayAI Echo content for 0.01 Circle devnet USDC in [transaction 3bQWcPCm…](https://explorer.solana.com/tx/3bQWcPCmY9S1E34J7EHt7HmfvDB7kvcfbAHmAQ8WsNqziqgWPTGTcuYA95ATnvPp1mC6bQxuhZKqFMEPGW5sr4aW?cluster=devnet). The backend verified the payer debit and merchant credit before marking it paid; repeating the task did not buy again. The first two attempts returned 402 because the merchant's USDC token account had not been initialized. After initializing that account on devnet, a local signed-transaction simulation passed and the third attempt settled. The client checks configured service URL and recipient, Circle devnet USDC, per-call and period caps, and a Founder-selected task ID. It journals a reservation before payment, checks the reported transaction's confirmation and USDC debit/credit, and blocks automatic retry when settlement is uncertain. A known receipt can be reconciled without a second purchase; a receipt-less rejected attempt can release its reservation only after blockhash expiry and a finalized signer-history scan. Every x402 purchase, task lookup, and period cap is now scoped to a company. Existing company-less x402 rows block the worker until explicitly migrated; Mercury never guesses their owner. The PER PDA float cannot sign standard x402 payments; the x402 signer is separate and its transfers are public. The signer's funded balance is its onchain maximum exposure; local caps are not contract-enforced. Run a single backend instance while using the local journal.

## Model and credentials

One model is enough for the first agent and invoice extraction. The chat agent defaults to Fireworks' OpenAI-compatible endpoint with `accounts/fireworks/models/kimi-k3` and `reasoning_effort: low`. Fireworks documents this as a thinking tier for Kimi K3; it does not disable reasoning. Kimi K3 passed a function-calling smoke test in this account. DeepSeek V4 Pro is an option only after its API access and tool behavior are verified for this account. `MERCURY_AGENT_REASONING_EFFORT` can be `low`, `high`, or `max`. Configure `MERCURY_FIREWORKS_API_KEY` only in the local environment. No provider key is committed to Git. A local compatible endpoint can be set with `MERCURY_AGENT_MODEL_URL` and `MERCURY_AGENT_MODEL`. Hosted inference requires `MERCURY_ALLOW_REMOTE_LLM=1`. The agent sends narrow tool results such as amounts and status to the model for follow-up reasoning, so the hosted provider receives that information. Invoice review also sends the selected invoice text to the configured model. A model API key pays for inference; it is not an agent payment key. The x402 adapter uses a separate signer and has a paid devnet proof.

For x402, set `MERCURY_ENABLE_X402_AGENT=1`, `MERCURY_X402_SERVICES_JSON`, and `MERCURY_X402_RPC_URL`. Set exactly one signer source: `MERCURY_X402_SIGNER_BASE58` or `MERCURY_X402_SIGNER_FILE` pointing to a mode-0600 local key file. Create the challenge with the same `allowX402Purchase`, selected service, and task ID sent to `/v1/agent/chat`. The wallet-signed message states the service URL, recipient, task, and maximum amount; changing these terms invalidates consent. Never reuse a company or AgentPolicy key for the isolated x402 signer. A model API key only pays for inference.

Before a public launch, compare invoice extraction accuracy on real examples, Nepali/English answers, latency, cost, and provider data handling. A live Fireworks tool-call smoke test passed; the backend tests use a mock and do not require a paid API key.

## Current assistant HTTP surface

`POST /v1/assistant/challenge` takes `{ "actor": "<wallet>" }` and returns a message to sign. `POST /v1/agent/chat` takes `{ "actor", "challengeId", "signature", "message", "grant?", "sessionId?", "requestedTool?", "requestAddress?", "selectedPayrollRunId?", "selectedPayrollItems?", "invoiceText?", "selectedVendorId?", "selectedPayeeId?", "selectedRecipient?", "selectedAmountMicro?", "paymentId?", "selectedX402ServiceId?", "x402TaskId?", "allowX402Purchase?" }` with `Authorization: Bearer <caller TEE token>`. A non-Founder supplies `grant`. The response includes `sessionId`; supply it with a fresh signed challenge for a follow-up. The session expires after 24 hours and is bound to company, wallet, grant, role, and scope. It stores recent verified answers and selected payment/payroll references encrypted with an auto-created local mode-0600 key; it does not remember authority to pay. `requestedTool` may require the model's first call to use a tool that is already allowed for the actor's live role and selected data; subsequent tool calls are model-directed. Invoice review requires a configured vendor registry. All four payee/amount/payment fields must be present to make the draft tool available. The backend verifies the one-use signature and grant, offers only allowed tools to the model, rechecks access for every call, and records a registered-payee draft only when the model amount matches the selected amount. The response includes the unsigned terms and `/v1/payment-flows/:paymentId/next`. `POST /v1/agent/audit` accepts a fresh wallet challenge, TEE token, active grant, and optional `limit` to read that actor's encrypted tool/result and failure trail for the same grant. The older `POST /v1/assistant/query` remains a read-only classifier endpoint. Treasury payment drafts remain unsigned; the optional Founder-assigned x402 tool can sign with its isolated wallet only.

The server is still local and configured for one company. This is a working backend tool loop, not yet a complete chat product. Model free text is untrusted; final answers are constructed from verified backend results. A user must review the selected payee and amount before requesting a draft. Signed chat requests have an in-process limit of five per minute and 30 per hour per wallet. The encrypted session and audit files are local to one backend instance; back up the key with the records. Assistant query, chat, and audit now require the MagicBlock TEE token's wallet claim to match the wallet that signed Mercury's challenge. The claim is not trusted by itself: the following private PER policy/grant read must validate the token. A live devnet check confirmed a genuine Founder token reads CompanyPolicy and a tampered token is rejected. This binding currently covers the assistant HTTP surface; broader wallet-to-token binding for all Mercury endpoints remains. For public deployment, move these records and the rate limit into shared durable storage, add durable replay protection, and review retention and key rotation.

The real HTTP follow-up proof passed on the configured Circle devnet USDC company: Founder wallet authentication, a fresh TEE token, two Fireworks Kimi calls choosing `get_payment_status`, encrypted session reuse without resending the request address, and a separately signed audit read. Both answers came from the live private request state (`executed`). A second live HTTP proof selected a synthetic registered-vendor invoice, got the real Kimi extraction and human-review suggestion, prepared a matching unsigned draft, read a two-item payroll run and its readiness, then inspected and bought one capped x402 response with a Founder-bound signed challenge. The isolated-wallet [purchase transaction](https://explorer.solana.com/tx/2qmvmhHTvR9HhVManC9GMdVJpiKTa7nm6zTwAD3XuBBz4RBXgc9TjzXp7V3QQM7bcePyHGYwgMtaYjcKRZRVW18j?cluster=devnet) settled; no company payment was sent.

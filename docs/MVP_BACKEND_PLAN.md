# Mercury backend and program completion plan

The next build phase excludes new Agent behavior. Each milestone must be repeatable for a newly configured Circle devnet USDC company, not just for the existing proof wallets.

1. **Company onboarding.** The policy, private snapshot, capped Finance grant, company funding, and recipient readiness now have stepwise backend endpoints. Signed transaction receipts are bound to prepared messages in a local journal. A fresh Circle devnet USDC company completed policy, snapshot, and Finance grant setup; private receive and recipient onboarding were verified through the HTTP endpoints. Wallet login/signing, safe recovery for abandoned receipt IDs, and multi-company server configuration remain.
2. **Team access and revocation.** Finance and Manager grants retain their capped spending paths. Manager approval now checks the request's encoded branch. Founder-issued Requester and Viewer grants are private, nonspending, and can be branch scoped; Requester activation and submission check the live grant. Finance, Manager, and member revocation planners scan historical PER requests and produce signed Founder-only ACL resets. A Requester/Viewer lifecycle, including denied submission and denied read after cleanup, passed on devnet. Remaining: background cleanup, member discovery and rotation, AgentPolicy reader cleanup after Finance revocation, and verification of each revoked wallet's read denial.
3. **Guided payment and tracking.** A local, mode-0600 flow journal derives one private request from each opaque payment ID and stores only public request identity plus a hash of private terms. It builds shell, delegation, ER permission, privacy activation, private submission, and approval in order, with receipt confirmation before every next state transition; approved flows create the existing execution journal. A Founder-driven Circle devnet USDC flow completed its whole request-to-payout-to-snapshot path, refused a replay, and the complete path was repeated on a newly configured Circle devnet company. Finance and Manager approve using their existing grants. On-demand history reconciles accessible jobs; an unsigned prepared payout can be rebuilt after one minute. Remaining: durable multi-company storage, background reconciliation and alerting, onboarding receipt recovery, recipient-balance evidence when available, and automatic refresh after receive/payout.
4. **Human-approved payroll.** A nine-item run is proven live: CSV row validation/preview, client-held roster, deterministic item IDs, approval split into eight-item and one-item signed PER transactions, existing period-budget reservations, nine one-time payouts, and per-item amounts/states. Weekly, biweekly, and monthly schedules use the first pay date and a chosen time zone; the backend stores a client-encrypted roster and exposes due cycles. Unlaunched cycles show `due` or `overdue`; launched cycles link to the run status endpoint, which reconciles each item against the private request and returns `preparing`, `approval_pending`, `paying`, `partial`, `failed`, `rejected`, or `paid`. Founder-signed, revision-checked schedule create/update/launch endpoints were exercised; a scheduled due cycle was launched twice under one run ID and both private payouts settled on devnet. The endpoint accepts up to 100 items, but the full bound is not live proven. The local run journal stores hashes rather than salaries or recipient wallets. An induced failed item was retried on devnet without paying the settled item again. Remaining: user-facing key recovery, reminders, and background reconciliation. Payouts still have individual signatures.

The first three milestones plus a working payroll run are the backend/program MVP. Frontend wallet login and signing are separate integration work. Mainnet requires additional security and recovery work described in [ARCHITECTURE.md](ARCHITECTURE.md).

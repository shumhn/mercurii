# Mercury backend and program completion plan

The next build phase excludes new Agent behavior. Each milestone must be repeatable for a newly configured Circle devnet USDC company, not just for the existing proof wallets.

1. **Company onboarding.** The policy, private snapshot, capped Finance grant, company funding, and recipient readiness now have stepwise backend endpoints. Signed transaction receipts are bound to prepared messages in a local journal. A fresh Circle devnet USDC company completed policy, snapshot, and Finance grant setup; private receive and recipient onboarding were verified through the HTTP endpoints. Wallet login/signing, safe recovery for abandoned receipt IDs, and multi-company server configuration remain.
2. **Team access and revocation.** Finance and Manager grants retain their capped spending paths. Manager approval checks the request's encoded branch. Founder-issued Requester and Viewer grants are private, nonspending, and can be branch scoped; Requester activation and submission check the live grant. The backend discovers existing private TeamGrants and guides Founder-signed revocation to the correct reader cleanup planner. Finance, Manager, and member planners scan historical PER requests; Finance cleanup also covers the treasury snapshot and AgentPolicies. A Requester/Viewer lifecycle, including denied submission and denied read after cleanup, passed on devnet. The AgentPolicy Finance-reader reset was separately proven on a revoked custom-mint AgentPolicy without restoring Agent access. Remaining: wallet UI/signing, optional background reminders, role rotation, and denied-read proof for each newly revoked wallet and target.
3. **Guided payment and tracking.** A local, mode-0600 flow journal derives one private request from each opaque payment ID and stores only public request identity plus a hash of private terms. It builds shell, delegation, ER permission, privacy activation, private submission, and approval in order, with receipt confirmation before every next state transition; approved flows create the existing execution journal. A Founder-driven Circle devnet USDC flow completed its whole request-to-payout-to-snapshot path, refused a replay, and the complete path was repeated on a newly configured Circle devnet company. Finance and Manager approve using their existing grants. On-demand history reconciles accessible jobs; an unsigned prepared payout can be rebuilt after one minute. Remaining: durable multi-company storage, background reconciliation and alerting, onboarding receipt recovery, recipient-balance evidence when available, and automatic refresh after receive/payout.
4. **Human-approved payroll.** A nine-item run is proven live: CSV row validation/preview, client-held roster, deterministic item IDs, approval split into eight-item and one-item signed PER transactions, existing period-budget reservations, nine one-time payouts, and per-item amounts/states. A readiness endpoint checks each recipient has a confirmed Mercury Private Payments onboarding receipt, without reading the employee's private balance, plus policy and snapshot coverage before creating a run. This enrollment plus readiness, a scheduled two-person run, one PER approval, and two private payouts were repeated live on devnet. Weekly, biweekly, and monthly schedules use the first pay date and a chosen time zone; `per_employee` schedules validate each due employee's own cadence and first pay date without persisting it outside the encrypted roster. Replacing that roster increments `rosterRevision`, and a launched run records its source revision. Unlaunched company-wide cycles show `due` or `overdue`; launched cycles link to the run status endpoint, which reconciles each item against the private request and returns `preparing`, `approval_pending`, `paying`, `partial`, `failed`, `rejected`, or `paid`. The run recovery endpoint rebuilds only items with an approved private request and a confirmed failed prior signature; it never retries a settled item. Founder-signed, revision-checked schedule create/update/launch endpoints were exercised; a scheduled due cycle was launched twice under one run ID and both private payouts settled on devnet. The endpoint accepts up to 100 items, but the full bound is not live proven. The local run journal stores hashes rather than salaries or recipient wallets. An induced failed item was retried on devnet without paying the settled item again. Remaining: user-facing key recovery, reminders, and background reconciliation. Payouts still have individual signatures.

5. **Selective payroll audit.** The Founder can create an expiring, revocable auditor capability for selected payroll runs. Mercury reads the selected private requests only while the Founder TEE session is present and stores the resulting frozen disclosure bundle encrypted under the auditor secret. The auditor can retrieve the frozen payroll evidence but cannot query live private accounts or move funds. The journal retains token hashes and encrypted content only. Unit coverage proves no disclosed employee wallet or salary plaintext reaches the durable audit journal. A frontend auditor portal and a live devnet audit-share proof remain.

The first three milestones plus a working payroll run are the backend/program MVP. Frontend wallet login and signing are separate integration work. Mainnet requires additional security and recovery work described in [ARCHITECTURE.md](ARCHITECTURE.md).

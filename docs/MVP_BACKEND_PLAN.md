# Mercury backend and program completion plan

The backend and contract milestones target a newly configured Circle devnet USDC company, not just the existing proof wallets. Frontend wallet integration is tracked separately.

1. **Company onboarding.** The policy, private snapshot, capped Finance grant, company funding, and recipient readiness now have stepwise backend endpoints. Signed transaction receipts are bound to prepared messages in a local journal. A fresh Circle devnet USDC company completed policy, snapshot, and Finance grant setup; private receive and recipient onboarding were verified through the HTTP endpoints. The backend now brokers wallet-signed TEE login and resolves registered companies per request. Wallet-facing signing UI, abandoned receipt recovery outside guided payments, and a fresh shared-server payout proof remain.
2. **Team access and revocation.** Finance and Manager grants retain their capped spending paths. Manager approval checks the request's encoded branch. Founder-issued Requester and Viewer grants are private, nonspending, and can be branch scoped; Requester activation and submission check the live grant. The backend discovers existing private TeamGrants and guides Founder-signed revocation and historical-reader cleanup through the same stepwise endpoint. Finance cleanup also covers the treasury snapshot and AgentPolicies. A new Circle USDC company completed Founder/Finance/Manager/Requester/Viewer setup, a Manager-approved and Finance-executed private payout, explicit Viewer sharing, and signed revocation/cleanup of all four grants. Repeated TEE reads denied each revoked member's old private record; Finance was also denied policy, snapshot, and AgentPolicy while Founder and active Agent retained their appropriate access. The unified endpoint returned `ready` for all four previously cleaned devnet grants. Remaining: wallet UI/signing, optional background reminders, role rotation, and broader failure/large-history coverage.
3. **Guided payment and tracking.** A local, mode-0600 flow journal derives one private request from each opaque payment ID and stores only public request identity plus a hash of private terms. It builds shell, delegation, ER permission, privacy activation, private submission, and approval in order, with receipt confirmation before every next state transition; approved flows create the existing execution journal. A Founder-driven Circle devnet USDC flow completed its whole request-to-payout-to-snapshot path, refused a replay, and the complete path was repeated on a newly configured Circle devnet company. Finance and Manager approve using their existing grants. On-demand history reconciles accessible jobs; an unsigned prepared payout can be rebuilt after one minute. Guided-flow unsigned receipts now record their blockhash and can be rebuilt only after 90 seconds, a finalized invalid-blockhash check, and a fresh request-state read. Signed receipts keep their original signature for reconciliation. An interrupted live devnet request shell waited on the same receipt before expiry, then produced a different receipt after expiry without broadcasting either transaction (`npm run devnet:guided-recovery-proof`). Older journal receipts without a blockhash still require manual inspection. A local reconciliation watch runner now paginates payment jobs and onboarding receipts, labels invoice-backed payment IDs without exposing invoice terms, reads payroll-run summaries, and emits only human actions such as `sign_snapshot_sync`, `retry_confirmed_failure`, or `recover_confirmed_failed_items`. It never signs, sends, or retries a transaction. A live fresh-company sweep reported the real Kimi invoice payout as `complete`. A prior expired unsigned request receipt was correctly surfaced as `inspect_target_before_rebuilding` and was not resent. Remaining: fresh multi-company traffic and restart proof on the encrypted database, hosted scheduling/notifications, broader onboarding receipt recovery, recipient-balance evidence when available, and automatic refresh after receive/payout.
4. **Human-approved payroll.** A nine-item run is proven live: CSV row validation/preview, client-held roster, deterministic item IDs, approval split into eight-item and one-item signed PER transactions, existing period-budget reservations, nine one-time payouts, and per-item amounts/states. A readiness endpoint checks each recipient has a confirmed Mercury Private Payments onboarding receipt, without reading the employee's private balance, plus policy and snapshot coverage before creating a run. This enrollment plus readiness, a scheduled two-person run, one PER approval, and two private payouts were repeated live on devnet. Weekly, biweekly, and monthly schedules use the first pay date and a chosen time zone; `per_employee` schedules validate each due employee's own cadence and first pay date without persisting it outside the encrypted roster. Replacing that roster increments `rosterRevision`, and a launched run records its source revision. Unlaunched company-wide cycles show `due` or `overdue`; launched cycles link to the run status endpoint, which reconciles each item against the private request and returns `preparing`, `approval_pending`, `paying`, `partial`, `failed`, `rejected`, or `paid`. The run recovery endpoint rebuilds only items with an approved private request and a confirmed failed prior signature; it never retries a settled item. Founder-signed, revision-checked schedule create/update/launch endpoints were exercised; a scheduled due cycle was launched twice under one run ID and both private payouts settled on devnet. The endpoint accepts up to 100 items, but the full bound is not live proven. The local run journal stores hashes rather than salaries or recipient wallets. An induced failed item was retried on devnet without paying the settled item again. Remaining: user-facing key recovery, reminders, and background reconciliation. Payouts still have individual signatures.

5. **Selective payroll audit.** The Founder can create an expiring, revocable auditor capability for selected payroll runs. Mercury reads the selected private requests only while the Founder TEE session is present and stores the resulting frozen disclosure bundle encrypted under the auditor secret. The auditor can retrieve the frozen payroll evidence but cannot query live private accounts or move funds. The journal retains token hashes and encrypted content only. Unit coverage proves no disclosed employee wallet or salary plaintext reaches the durable audit journal. A settled Circle devnet payroll run also completed live create -> auditor open -> Founder revoke -> denied reread; the proof verifies that metadata outside the encrypted envelope contains neither employee recipient, salary amount, nor auditor bearer token. A frontend auditor portal remains.

6. **Invoice Agent Suggest.** Model extraction is checked against the registered vendor name, fixed payout wallet, and invoice cap. A keyed local journal binds one vendor invoice number to one guided payment ID; a repeated suggestion cannot create a second private request, and changed terms stop for review. The Founder-facing Kimi HTTP flow proved synthetic invoice review and an unsigned vendor draft. A full HTTP devnet journey used a deterministic local model for extraction and the real Mercury contract for payment: Founder-signed invoice review → six guided request/approval transactions → [private payout `3v2YP...`](https://explorer.solana.com/tx/3v2YPoxjd4HgWdcnfzSeDB2ny52fqFZ5J4CG3X8Ut86W5M4URAaxxKYSgDmnNzV83RfpsSrUhugiyn5eE8g4wnBt?cluster=devnet) → Founder-signed snapshot refresh → reconciliation sweep. The invoice bound payment ID `1b38e78f-dd28-42a6-8901-1880978d5ec2`; repeat review returned the same ID, changed amount was blocked, and payout retry built no second transaction. The run resumed after a backend restart and observed the same settled payment. A second live proof issued an Agent wallet a private Requester grant, then completed Agent-signed request creation/submission with Founder-signed privacy activation, approval, and [private payout `2hjcE...`](https://explorer.solana.com/tx/2hjcEYopPbVvT83vZru4btdD8bNm5pQX9bDfFxLCs2H1z1w5eee9gn742qEryjX6oWNP6PQS6hnfqg7ahdreTs9m?cluster=devnet). It also proved duplicate and changed-invoice rejection, no second payout, snapshot sync, and reconciliation after restart. This exposed and fixed a guided-flow bug: Requester role checks now read the Agent's private grant instead of requiring its token to read Founder-only CompanyPolicy. Both payout proofs use deterministic local invoice extraction; the real Kimi model was exercised separately for the review/draft flow. The backend holds no Agent treasury signing key. Invoice file ingestion and authenticated document storage remain.

The first three milestones plus a working payroll run are the backend/program MVP. Frontend wallet login and signing are separate integration work. Mainnet requires additional security and recovery work described in [ARCHITECTURE.md](ARCHITECTURE.md).

## Multi-company boundary

The HTTP server resolves each request to an environment default, a static operator registry, or a Supabase-registered onchain company. The registration endpoint verifies the founder-derived policy shell; the request selector accepts `x-mercury-company`, `body.company`, or `?company=` and rejects conflicts. The selected company's mint is used by payment, receive, onboarding, and recipient routes. Wallet-backed TEE login was exercised over HTTP for a Supabase-registered company with no default environment company. Payment-flow reads are company-scoped; an existing encrypted flow belonging to one company was absent under another company's ID lookup.

The shared server completed a **new private receive → new Founder-approved guided payout → snapshot sync → reconciliation → restart** run for an existing funded Circle devnet company, using its Supabase registry entry and database-primary records with no default company environment setting. The recipient's private balance increased by 10,000 micro USDC. The [receive](https://explorer.solana.com/tx/4buRhdSDesBWr4Y9J8bYoX2Ryzgwd9AWDqPaqHkzELJNaFEFFhHTcC7oFaWV1vDXgXTAMaiipVhQXGx3B5TMvfDo?cluster=devnet) and [private payout](https://explorer.solana.com/tx/3yKqPTHkxeUz6cexPXXbyP6VibRW7u5DzgWGKnX2owvRBm2ZonnWD1zmkh2x5c7aCbxNRjXLmuh6DqgLHPzUA7gf?cluster=devnet) independently returned finalized/no error on their respective base and PER RPCs. `npm run devnet:shared-company-loop-proof` is the guarded harness; it refuses to pay twice after a settled run. A brand-new company's setup and funding through the shared server still need a separate acceptance run. Legacy local audit-share and x402 journals, plus historical records not migrated for a company, require explicit migration/operational handling.

## Next engine acceptance run

The invoice-to-payout path has been proven in both Founder-requester and delegated Agent-requester forms on the existing Circle devnet USDC company. Expired unsigned guided-flow recovery has been proven against an interrupted live request shell. The next live acceptance run is `npm run devnet:real-agent-invoice-proof`: it uses Fireworks `accounts/fireworks/models/kimi-k3` with its thinking tier for invoice extraction, then follows the delegated Agent request, Founder privacy activation/approval, private payout, snapshot sync, restart-safe reconciliation, duplicate rejection, changed-terms rejection, and second-payout prevention. It requires a newly provisioned, funded devnet company; the script refuses to start a new proof when a prior proof state exists for that company, unless `MERCURY_REAL_AGENT_PROOF_RESUME=1` is explicitly supplied to recover the exact interrupted run. Configure `MERCURY_REAL_AGENT_PROOF_COMPANY`, `MERCURY_REAL_AGENT_PROOF_FOUNDER_KEYPAIR`, `MERCURY_REAL_AGENT_PROOF_AGENT_KEYPAIR`, `MERCURY_REAL_AGENT_PROOF_RECIPIENT`, and `MERCURY_FIREWORKS_API_KEY`. The API key is passed only to the temporary local backend process and must never be committed. The Agent signs request-shell and delegation transactions, so the devnet harness ensures it has a 0.1 SOL base-layer bootstrap from the Founder; that public SOL setup transfer is separate from the private USDC payment path. The proof completed on company `EQou…KTk`: Kimi extracted the registered 0.01 USDC invoice, the Agent submitted the private request, Founder approved it, and [private payout `5p7PY…`](https://explorer.solana.com/tx/5p7PYtrSXS2TatbWarGwngj37qyuWHBfhUxGuK6LbBjSCF3NQrHkRiAZ1vXEnTFptRxR8pGZzAJnuej8ANLQ6z6C?cluster=devnet) settled; the snapshot was 990000 micro USDC and reconciliation found the same settled payment.

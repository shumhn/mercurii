# Mercury backend and smart contract

Mercury is private USDC operations for onchain teams: a company treasury, payment approvals, and bounded agent spending. This repo is a **devnet implementation in progress**. It is not ready for real funds.

## Current contract

The Anchor program in `programs/mercury/src/lib.rs` has five PER state account types:

| Account | Readers | Function |
| --- | --- | --- |
| CompanyPolicy | Founder, Finance, and explicitly delegated Manager readers | USDC mint, period budget, reserved/spent amount, treasury authority |
| TeamGrant | Founder, member, grantor, and permitted child readers | Private Finance/Manager spending grants and nonspending Requester/Viewer grants; parent link and revocation |
| PaymentRequest | Founder plus explicitly assigned Requester, Finance, Manager, or Viewer readers | Private recipient/amount; submit, approve, execute, reject |
| AgentPolicy | Agent, Founder, Finance until Agent revocation or reader cleanup | Separate token float authority, one approved recipient, per-payment and period caps; Founder can remove the Finance reader, preserving a revoked Agent's exclusion |
| TreasurySnapshot | Founder, Finance | Manually synchronized private view of the canonical company token account balance and observation slot |

Each account starts as a non-confidential shell on Solana base, is delegated to the same TEE PER, receives an ER-local permission, and is made private **before confidential fields are written**. PER permissions control reads. The Mercury program separately checks signer and business policy. Founder/Finance/requester/agent pubkeys and account creation remain public in this prototype.

Founder can approve and execute directly. Finance needs an active Founder-issued TeamGrant with recipient allowlist and amount/period caps. Finance may issue a narrower Manager grant only when permitted; Manager can approve a privately shared request but cannot execute from the treasury. Approval reserves the company budget. `execute_payment` checks approved period, request status, recipient owner, mint, source authority, available reserve, and the executing Finance grant when applicable. It then makes a PDA-signed SPL Token CPI and updates request/budget state in the same PER transaction. A failed CPI must revert the state update. The agent's `agent_pay` path still requires its own key and separate capped float. Agent float funding/reclaim is Founder-only in the current permission revision; an earlier devnet proof used Finance before that restriction.

Existing requests created before branch IDs remain readable under their current ACL until cleanup, but a Manager cannot approve them under the new branch check; Founder or Finance must handle them. A non-Founder requester with an unfinished historical request needs a live Finance or Requester grant to submit after this upgrade.

The token path has been exercised end to end on the private devnet ER with **both a locally minted six-decimal test token and Circle devnet USDC**. The company PDA received through MagicBlock's hosted payment builder, Finance executed an approved payout through Mercury's PDA-signed SPL CPI, and a recipient withdrew with their own wallet. The separate AgentPolicy-owned float was funded and spent with Circle devnet USDC. Revocation and reclaim were exercised with the custom test mint; those two actions have not been repeated with Circle USDC. Do not use real funds.

For employee, contractor, and vendor payouts, the current Mercury program sends to a recipient token account already on the same PER. The recipient can read their own balance through the TEE and build a wallet-signed withdrawal through MagicBlock's Private Payments API. Both recipient operations were verified on devnet with the custom test mint and Circle devnet USDC; an outsider was denied the private balance. A frontend wallet-login flow remains unimplemented. Direct company-PDA-to-base payouts through the API remain unimplemented.

The payroll API groups up to 100 employee requests into one run. The Founder creates the run; recipient wallets and salaries are passed on each item setup call and are not written to the local journals. Approval transactions contain up to eight items each, so a larger run needs multiple wallet signatures. Each confirmed approval reserves its items through the existing company budget checks. Each payout then uses its own retry-safe payment job. The run reports each item's private request and payout state. The 100-row bound protects the HTTP request and local journal; it is not a MagicBlock payroll limit. A nine-person run with two approval transactions and nine payouts has live devnet proof; 100 items are not live proven. The schedule journal can hold a client-encrypted roster, but key recovery and automatic payout execution remain open. HR, tax, payslips, and fiat payroll are outside this build.

Payroll schedules support weekly, every two weeks, monthly, and `per_employee` cycles. A `per_employee` roster keeps each employee's cadence and first pay date inside the caller-encrypted roster, so one company can pay different employees on different dates. The backend validates only the due employees supplied for a launch and does not persist their plaintext schedule. Each roster replacement receives a new `rosterRevision`; a launch is bound to that revision, so an old roster cannot create a run after an update. The monthly 29th–31st date falls on the month's last day when needed. A Founder still reviews, signs approvals, and signs each private payout; a calendar date never moves funds by itself.

## Current backend

`backend/` is a local, noncustodial HTTP service. It has:

- `POST /v1/companies/register`: checks the founder-derived company policy shell on devnet and registers its public founder/mint identity in Supabase. Subsequent requests select the company with `x-mercury-company`, `body.company`, or `?company=`; conflicting selectors are rejected. An environment-configured company remains the default when no selector is supplied.
- `POST /v1/auth/tee-login/challenge` and `/v1/auth/tee-login`: a wallet signs MagicBlock's challenge; Mercury verifies the signature and checks the returned token names that wallet. The token still grants only the reads allowed by PER. These endpoints work for a registered company without a default company environment setting.
- `POST /v1/onboarding/next`: with a Founder TEE bearer token and `{ "actor": "<Founder wallet>", "finance": "<Finance wallet>", "monthlyLimitMicro": 100000000, "agentCapMicro": 10000000 }`, reads base, router, and PER state for the selected Circle devnet USDC company. It returns one next unsigned setup transaction, `wait` while delegation propagates, or `ready` when the policy and snapshot are private. The client signs/submits, confirms the signed transaction receipt, and calls again. It verifies the existing Founder/Finance/mint before continuing and never sets confidential limits before PER privacy.
- `POST /v1/onboarding/finance-grant/next`: with a Founder TEE bearer token and `{ "actor": "<Founder wallet>", "finance": "<Finance wallet>", "grantId": "1", "perPaymentCapMicro": 1000000, "periodCapMicro": 10000000, "recipients": ["<approved wallet>"], "mayDelegate": false }`, returns one next unsigned root Finance grant transaction, `wait`, or `ready`. The client keeps the same `grantId` while calling again after each confirmed step. The backend checks the private company policy, matching grant PDA/identity, selected PER, recipient list, and caps; it rejects changed terms on an already active grant. A revoked grant requires a new ID. The existing Circle devnet grant was read-only verified as `ready`; a fresh grant was dry-run through its first unsigned builder step.
- `POST /v1/onboarding/manager-grant/next`: Finance supplies `{ "actor": "<Finance wallet>", "finance": "<Finance wallet>", "manager": "<Manager wallet>", "grantId": "2", "parentGrant": "<active Finance grant>", "branchId": 17, "perPaymentCapMicro": 100000, "periodCapMicro": 500000, "recipients": ["<approved wallet>"] }` with its own TEE token. The endpoint derives the branch PDA, checks the parent grant's delegation right, recipient list, caps, and scope, then builds one Finance-signed step at a time. Manager approval/rejection requires a payment request ID carrying the same branch in its upper 24 bits.
- `POST /v1/onboarding/member-grant/next`: Founder supplies `{ "actor": "<Founder wallet>", "member": "<wallet>", "role": "requester", "grantId": "3", "branchId": 17 }`; `viewer` is the other role and `branchId` may be omitted for company-wide access. The response guides public shell, PER delegation, private permission, and zero-spend grant activation. Employees and contractors need a Requester grant to activate and submit their own private request; a Viewer grant permits only explicitly shared record reads. The Founder issues these grants directly in this MVP.
- `GET /v1/team-members`: with a TEE token, discovers private TeamGrants from PER state and returns only grants that the same token can read directly. This survives a local journal restart. The Founder sees the company roster; a limited member sees only grants allowed by PER permissions.
- `POST /v1/team-grants/:grantAddress/revoke/next`: Founder supplies `{ "actor": "<Founder wallet>" }`. For an active Finance, Manager, Requester, or Viewer grant it returns one unsigned revoke transaction and receipt ID. After confirmation, call the **same endpoint** for one historical-reader cleanup transaction at a time until it returns `ready`. It reuses pending receipts instead of preparing duplicate steps. The Founder signs/broadcasts each transaction and confirms its receipt; read denial should be checked before considering removal complete. The older role-specific cleanup planner endpoints remain available for manual inspection.
- `POST /v1/onboarding/company-funding/next`: Founder supplies a stable `fundingId`, `payer`, `amountMicro`, and `targetBalanceMicro`. If a fresh private snapshot already meets the target it returns `ready`; otherwise it builds a payer-signed private receive, waits for its signed base receipt, then builds a Founder-signed snapshot sync until the private observed balance meets the target. A confirmed base transaction alone never marks treasury funding ready.
- `POST /v1/onboarding/recipient/next`: with the recipient's TEE token and `{ "recipient": "<wallet>", "payer": "<wallet>", "amountMicro": 1, "depositId": "initial" }`, returns `needs_deposit` with a payer-signed private deposit, `wait` while its receipt/credit is unresolved, or `ready` only when the recipient's PER token account can be read. It pins the company PER validator.
- `POST /v1/onboarding/receipts/:id/confirm`: the client submits its **signed** transaction bytes after broadcast. The local backend verifies the signatures and exact prepared message, queries base or PER confirmation, and saves only public addresses, operation, message hash, signature, and status in `backend/.state/`. It does not store keys, salary data, private recipient lists, or raw transaction bytes. `POST /v1/onboarding/receipts/:id/reconcile` polls a recorded signature after a timeout or restart; it can also bind the original signed bytes if the initial confirmation call was lost. A receipt without a known signature needs the original signed bytes or target-state inspection before rebuilding. Never send a second deposit merely because an RPC lookup returned no status.
- `POST /v1/access/finance-revocation-cleanup/plan`, `/v1/access/manager-revocation-cleanup/plan`, and `/v1/access/member-revocation-cleanup/plan`: after revoking the relevant grant, the Founder submits its address with a Founder TEE token. The planners scan private requests, including records absent from the local journal, and prepare batches of Founder-signed ACL resets. Each affected request becomes Founder-only; the Finance planner also updates the balance snapshot and removes Finance from each AgentPolicy. A revoked Agent remains excluded. Confirm receipts and repeat until `ready`, then explicitly re-share any active teammates. A stale unsigned or pending cleanup may be rebuilt after five minutes. Check denied reads with the revoked wallet's TEE token before treating privacy cleanup as verified.
- `POST /v1/access/request-viewer/build`: Founder supplies a private `request`, active `viewerGrant`, `viewer`, and an explicit `includeRequester` choice. Keeping requester access requires its active grant. The endpoint builds a Founder-signed ACL change; it never gives the Viewer spending or approval rights. To remove a Viewer, revoke its grant and run member cleanup.
- `POST /v1/access/policy-readers/restore/build`: Founder supplies an active Finance grant to rebuild the company policy readers from that grant's Finance member and active child-reader list. This is a signed repair/rotation step; a revoked grant cannot restore access.
- `POST /v1/private-receive/build`: asks MagicBlock's Private Payments API for a **payer-signed, unsigned** `base → ephemeral` USDC transaction to the configured company address. It fixes visibility to `private` and rejects a builder response that omits the payer from required signers.
- `POST /v1/recipient-onboard/build`: builds the same kind of private USDC deposit to an on-curve employee, contractor, or vendor wallet on Mercury's selected PER. The caller supplies `payer`, `recipient`, and a positive `amountMicro`; the payer signs and funds the initial deposit. A submitted base transaction is not proof that the recipient's private balance is ready: read `GET /v1/recipient-balance/:wallet` with the recipient's TEE login token before paying them.
- `POST /v1/recipient-withdraw/build`: builds an **unsigned**, recipient wallet-signed withdrawal from the configured PER validator to that wallet's base token account. It rejects PDA owners, signer mismatches, and wrong-validator responses. It does not withdraw company PDA funds.
- `GET /v1/recipient-balance/:wallet`: reads that wallet's canonical token account on the TEE with the caller's TEE bearer token; the PER denies outsiders. It does not accept a company PDA as recipient.
- The receive builder also rejects a response routed to a PER validator other than the configured company validator.
- `POST /v1/operations/build`: builds unsigned Mercury company initialization, privacy setup, TeamGrant lifecycle, request, approval, budget, and agent transactions for the configured company. The caller signs and submits to the returned base or TEE endpoint. Private operations require a TEE bearer token. The backend holds no Founder, Finance, Manager, or Agent key. `initializeCompany` requires the configured Founder, Finance wallet, mint, and correctly derived company PDA. `setRequestReaders` and `setSnapshotReaders` let Founder change individual private account ACLs; the root Finance cleanup planner fans those updates out across discovered requests and snapshot.
- `POST /v1/payment-flows/:paymentId/next` is the guided request path. Pass one UUID v4 plus `{ "actor", "requester", "recipient", "amountMicro", "includeFinance", "manager" }` on every call. It derives exactly one request PDA from the payment ID and requester, returns one unsigned step at a time, and returns a receipt ID for every signed transaction. The client sends each transaction to its returned base or PER endpoint, confirms its receipt through `/v1/onboarding/receipts/:id/confirm`, then calls `next` again. The order is shell → delegation → ER permission → privacy activation → private submit → human approval → linked payment job. Recipient and amount are held only in the caller request and unsigned private transaction; the local flow journal stores only a hash of those terms, public identifiers, and the request address. `GET /v1/payment-flows/:paymentId` recovers state after restart. A submitted request may be approved by Founder, Finance with an active root grant, or Manager with an allowed parent grant. Completed flows return the linked payment-job paths.
- `POST /v1/payees` registers an opaque `payeeId`, `kind` (`employee`, `contractor`, or `vendor`), optional `teamId`, and wallet owner. `GET /v1/payees` lists those records; `POST /v1/payees/:id/deactivate` stops new matching. The caller retains the wallet address; the mode-0600 local registry stores a recipient fingerprint, not the raw address. Pass optional `payeeId` to the guided payment flow to bind the payment to that payee, and read the classification in payment history. This is organization metadata; treasury policy and PER ACLs still enforce payment authority and privacy.
- `POST /v1/payroll-runs` takes a UUID `runId`, Founder `requester`, and 1–100 `{ "recipient", "amountMicro" }` employee items. It returns a stable payment ID and guided flow URL for each item. Submit each private request using its flow URL and the original terms. `POST /v1/payroll-runs/:runId/approve` takes `{ "actor": "<Founder or permitted Finance>", "grant": "<Finance grant if needed>" }` and returns an unsigned PER transaction for up to eight pending approvals. The wallet signs, submits, and confirms it using the ordinary receipt route, then repeats the approval call until no approvals remain. Each chunk is atomic; a whole run spanning chunks is not. `GET /v1/payroll-runs/:runId` returns per-item request and payout states; approved items use their existing `/v1/payment-jobs/:id/prepare` and `/submit` endpoints. The roster and salary amounts remain client-held; the local run journal stores only a hash and request identities. There is no separate onchain PayrollRun account.
- `POST /v1/payroll-runs/preview` takes `{ "csvText": "wallet,amount_usdc..." }`, validates each employee wallet and exact six-decimal USDC amount, reports duplicate/invalid rows, totals, and advisory private treasury/budget coverage. `POST /v1/payroll-runs/readiness` takes transient `{ "items": [{ "recipient", "amountMicro" }] }` and checks each recipient has a confirmed Mercury Private Payments onboarding receipt, plus current policy headroom and treasury snapshot. It does not read employee balances. It returns `ready`, `needs_onboarding`, or `unavailable` per employee and never writes the roster. An employee must use Mercury's recipient-onboarding flow before being marked ready. Use the returned valid items with `POST /v1/payroll-runs`; any error blocks a clean run instead of silently skipping a salary. `GET /v1/payroll-runs/:runId` returns each employee recipient, salary amount, request, and payout state to the private Founder/Finance reader. It does not expose the employee's unrelated private wallet balance. `POST /v1/payroll-runs/:runId/recover` reconciles selected failed item IDs and builds replacements only where the private request remains approved and the prior signature is confirmed failed. **Each payout still needs its own signed execution.**
- `GET /v1/payroll-runs` lists saved run IDs, creation times, item counts, and status URLs to a caller whose TEE token can read the private company policy. After a server restart, open a run's status URL to find its pending, failed, and settled items. Submitting unfinished private requests still requires the original client-held roster terms. Run lookup does not expose roster wallets or salary amounts in the local journal.
- `POST /v1/payroll-schedules` stores `{ "actor": "<Founder>", "scheduleId": "<UUID v4>", "name": "Team payroll", "cadence": "weekly|biweekly|monthly|per_employee", "firstPayDate": "YYYY-MM-DD", "timeZone": "Asia/Kathmandu", "encryptedRoster": { ... }, "signature": "<Founder signature>" }`. The caller encrypts the roster before upload and keeps its passphrase. `GET /v1/payroll-schedules` lists dates and up to 12 recent due cycles; a `per_employee` schedule returns no server-calculated dates because individual cadence remains encrypted. `GET /v1/payroll-schedules/:id` also returns the encrypted roster for client-side recovery. `PATCH /v1/payroll-schedules/:id` with signed `{ "actor": "<Founder>", "scheduleId": "<same URL ID>", "expectedRevision": 0, "paused": true|false }` pauses/resumes new launches; replacing `encryptedRoster` increments `rosterRevision`. `POST /v1/payroll-schedules/:id/launch` takes signed `{ "actor": "<Founder>", "scheduleId": "<same URL ID>", "payDate": "<due date>", "rosterRevision": 1, "requester": "<Founder>", "items": [{ "recipient": "<wallet>", "amountMicro": 1000000 }] }`; `per_employee` items also include `cadence` and `firstPayDate`, which are validated as due then discarded before the run journal is written. It returns the ordinary guided payroll run. Sign the bytes from `payrollScheduleMessage(operation, company, body)` in `backend/src/payroll-schedule-auth.ts` with the Founder wallet and attach its base58 signature; create/update/launch are separate domains. The caller decrypts the saved roster locally with `openPayrollRoster`, previews it, then submits its rows. This schedule metadata and ciphertext are held in the mode-0600 backend journal; salary amounts still reach the backend transiently on launch and are stored only as hashes in the flow/run journals. Losing the passphrase prevents roster recovery.
- `GET /v1/payment-jobs?limit=50` reads accessible private requests and payout signatures again, reconciles each local job, and reports stale snapshot status. Records outside the caller's PER read scope are omitted and counted as unavailable.
- `POST /v1/payment-jobs/:id/rebuild` recovers an unsigned payout preparation after one minute **and only when the PER RPC proves its blockhash expired**. It reads the private request again and only clears the local preparation if the request is still approved and no signed transaction was recorded. Older journal entries without a stored blockhash require manual inspection. Submitted payouts keep their original signature and must be reconciled or rebroadcast with the same signed bytes. The journal retains confirmed failed attempt signatures when a replacement is prepared.
- `POST /v1/reconciliation/run` with a Founder TEE token polls paginated payment jobs and onboarding receipts after a restart or timeout. Pass optional `{ "paymentOffset": 0, "receiptOffset": 0, "limit": 20 }` and follow `nextPaymentOffset` and `nextReceiptOffset` until both are `null`. Each payment returns its private request state, saved signature status, and a safe next action such as `retry_confirmed_failure`, `check_blockhash_before_rebuild`, or `sign_snapshot_sync`. A missing signature or RPC error never triggers a replacement transfer. This endpoint only observes and updates local receipts; the wallet still signs a payout or snapshot sync.
- Run `MERCURY_FOUNDER_KEYPAIR=<local-key-file> npm run reconcile` from `backend/` for one full sweep, or add `-- --watch` to poll every minute while that local process runs. Set `MERCURY_BACKEND_URL` if the server is not on port 8787. The command refreshes TEE login for each sweep and prints counts/actions without salaries or raw private requests. It never signs or broadcasts payments. Keep the Founder key file outside Git.
- `GET /v1/transactions/:signature?chain=base|ephemeral`: reports chain confirmation or failure. `paymentSettled: null` means chain confirmation alone does not prove the full private transfer settled.
- `GET /v1/payments/:requestAddress/status`: reads the ACL-protected Mercury request with the caller's TEE token. `paymentSettled: true` only when the request is `executed`: the program marks it executed in the same PER transaction as its SPL token transfer. This reports the request state, not an independently matched transaction signature or a fresh recipient balance.
- `POST /v1/payment-jobs`: with an authorized TEE token and `{ "paymentId": "<random UUID v4>", "request": "<private request PDA>" }`, binds one opaque payment ID to one onchain request. The backend verifies the private request identity and rejects an ID or request already bound elsewhere. `POST /v1/payment-jobs/:id/prepare` takes `{ "actor": "<Founder or Finance wallet>", "grant": "<Finance grant if needed>" }` and returns one unsigned execution. `POST /v1/payment-jobs/:id/submit` takes `{ "signedTransactionBase64": "..." }`, verifies the exact prepared message and signer, records its signature **before** PER broadcast, and allows resending only those same signed bytes while outcome is uncertain. `GET /v1/payment-jobs/:id` reconciles the recorded signature with the private request state; only `executed` means settled. A confirmed signature is separately reported as `signatureLinked` when the same request is executed. The local `backend/.state/payments.json` stores public IDs, addresses, signature, hashes, and state with mode 0600; no amount, recipient, or signed transaction bytes. Keep the unsigned transaction until signed and submitted; the `rebuild` route recovers an abandoned unsigned preparation.
- After settlement, `GET /v1/payment-jobs/:id` compares the payout confirmation slot with the private treasury snapshot and reports `snapshotNeedsSync`. `POST /v1/payment-jobs/:id/snapshot-sync` with `{ "actor": "<Founder wallet>" }` prepares one unsigned Founder-signed sync when needed; the caller broadcasts it on the PER and confirms its receipt through `/v1/onboarding/receipts/:id/confirm`. Calling again returns `ready` once the snapshot slot covers that payout. This refresh is wallet-driven; it does not prove the balance includes transfers made after the snapshot slot.
- `POST /v1/payments/:requestAddress/build-execution`: with a Founder or Finance TEE bearer token and `{ "actor": "<wallet>", "grant": "<Finance TeamGrant address when Finance acts>" }`, reads the approved request and company policy, derives the canonical company and recipient USDC token accounts, and builds the unsigned `executePayment` PER transaction. The actor signs; the contract rechecks approval, grant, budget, mint, recipient ownership, and token transfer. The last synchronized treasury snapshot is advisory because it can be stale.
- `GET /v1/delegation/:address`: asks the MagicBlock router for delegation status and ER routing information.
- `GET /v1/treasury-snapshot`: reads the PER-private balance snapshot with a Founder/Finance TEE bearer token. Its `updatedSlot` is the last manual sync slot; the value can be stale after a transfer.
- `GET /v1/company-policy`, `GET /v1/team-grants/:address`, `GET /v1/payment-requests/:address`, `GET /v1/agent-policies/:address`: decode private PER accounts using the caller's TEE bearer token. MagicBlock ACL controls access; the backend checks that each account belongs to the configured company.
- `POST /v1/agent/invoice-suggestions`: with a separate Agent API key, accepts `{ "invoiceText": "...", "vendorId": "..." }` and calls a configured OpenAI-compatible model to extract invoice fields. It checks the model's vendor and amount against a server-side vendor registry and selects the registered recipient itself. It binds the vendor's invoice number to one payment ID and returns that ID, the private request address, and terms for `/v1/payment-flows/:paymentId/next`. A repeat with the same terms returns the same ID; changed amount or recipient requires manual review. The mode-0600 invoice journal holds keyed fingerprints, never invoice text, number, wallet, or amount in plaintext. This is **Suggest only**: the endpoint does not sign, submit, approve, or pay. The Agent needs a Founder-issued Requester grant and its own signing key for request steps; Founder activates privacy and Founder/Finance reviews, approves, and executes separately.
- `POST /v1/assistant/challenge` and `POST /v1/agent/chat`: when `MERCURY_ENABLE_FINANCE_ASSISTANT=1`, a wallet signs a one-use challenge and supplies its own TEE bearer token. The Kimi K3 thinking agent chooses scoped treasury, payment, payroll-readiness and invoice-review tools, or prepares one unsigned draft for a user-selected registered payee. Backend code checks the live role and Finance cap before each action; a human still reviews, signs, and completes the guided payment flow. Follow-ups pass the returned `sessionId` with a fresh signed challenge; the 24-hour encrypted session remembers verified answers and selected records, then refreshes live facts. `POST /v1/agent/audit` returns the active actor/grant's encrypted tool trace after a fresh challenge. Signed chat calls are limited per wallet in this backend process. An optional Founder-assigned x402 tool uses a separate tiny signer, approved service, and local caps. The older `POST /v1/assistant/query` remains a read-only classifier. See [the agent plan](docs/AGENT_PLAN.md).
- `POST /v1/agents/:agentPolicyAddress/build-payment`: with the Agent's TEE token and `{ "actor": "<Agent wallet>", "amountMicro": 1000 }`, checks the private AgentPolicy's signer, revocation state, USDC mint, recipient, and cap, then derives the float/recipient token accounts and builds an unsigned `agentPay` transaction. The Agent signs it; the contract checks the policy again. The Circle USDC Agent funding and spend path has been exercised on devnet.
- `GET /health`.

The backend never holds a company treasury or AgentPolicy spending key. The optional x402 adapter holds a separate, deliberately small signer key when enabled; its local caps are not contract-enforced. A real 0.01 Circle devnet USDC x402 purchase was verified on devnet (see below). The backend does not approve company payments or report an unsigned/queued transfer as settled. The hosted builder response must be inspected by the payer wallet before signing. The backend binds to `127.0.0.1` by default and is not a public production API. Private operation arguments pass through this local backend in plaintext; a production client should construct those transactions locally and send them directly to the TEE.

```sh
cd backend
npm ci
MERCURY_COMPANY_ADDRESS=<company-policy-PDA> \
MERCURY_FOUNDER_ADDRESS=<founder-wallet> npm start
npm run typecheck
npm test
```

`MAGICBLOCK_CLUSTER` defaults to `devnet-private`, which the live hosted builder accepted. `MERCURY_COMPANY_ADDRESS` must be the actual Mercury policy PDA. Private receive and recipient onboarding require `MERCURY_ENABLE_EXPERIMENTAL_RECEIVE=1`; recipient withdrawal requires `MERCURY_ENABLE_EXPERIMENTAL_WITHDRAW=1`; token-moving Mercury builders require `MERCURY_ENABLE_EXPERIMENTAL_TOKEN_CPIS=1`. They remain off by default until the exact deployment mint and custody accounts are checked. Withdrawal uses `MERCURY_COMPANY_MINT` and pins the company TEE validator; verify this mint against the deployed policy before enabling. Both deposit routes additionally require that mint to equal Circle's devnet USDC mint. The current custom-mint proof company must not be used with the USDC deposit routes. These switches are for local devnet use.

The invoice Suggest route additionally needs `MERCURY_ENABLE_INVOICE_AGENT=1`, `MERCURY_AGENT_API_KEY`, `MERCURY_SUGGEST_AGENT_ADDRESS`, `MERCURY_LLM_URL`, `MERCURY_LLM_MODEL`, and `MERCURY_VENDOR_REGISTRY_JSON`. The registry maps a vendor ID to `{ "name": "Acme Cloud LLC", "recipient": "<wallet>", "maxInvoiceMicro": "50000000" }`. By default, the model URL must be loopback (`localhost`, `127.0.0.1`, or `::1`); setting `MERCURY_ALLOW_REMOTE_LLM=1` explicitly permits sending invoice text to another host, with optional `MERCURY_LLM_API_KEY`. The backend neither persists invoice text nor stores an Agent signing key. It detects repeated invoice numbers within one vendor but does not verify invoice authenticity or schedule autonomous work. A model can misread an invoice, so a human must review the draft and sign the required steps; the onchain approval and payment checks remain authoritative.

Set `MERCURY_ENABLE_FINANCE_ASSISTANT=1`, `MERCURY_ALLOW_REMOTE_LLM=1`, and `MERCURY_FIREWORKS_API_KEY` to use the chat agent's default Fireworks endpoint and Kimi K3 thinking model. Fireworks requests use low thinking effort by default; `MERCURY_AGENT_REASONING_EFFORT` accepts `low`, `high`, or `max`. `MERCURY_AGENT_MODEL_URL` and `MERCURY_AGENT_MODEL` can select another compatible endpoint/model. Keep the API key out of Git. The agent sends the user's message and narrow tool results, including private amounts or payment status, to the configured model; invoice review additionally sends the selected invoice text. The older read-only classifier uses `MERCURY_LLM_URL`, `MERCURY_LLM_MODEL`, and optional `MERCURY_LLM_API_KEY` and sends only the question.
